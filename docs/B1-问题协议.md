# B1 问题协议 —— 已实现 / 未实现

对应方案第 3 节 B1。基准提交 `f33bce9`。

## 已实现

### 1. 固定三类问题（分类决定数字怎么算）

| 分类 | 用途 | 是否计入推荐判断 |
|---|---|---|
| `branded_awareness` 认知题（带品牌名） | 核对模型对品牌的描述是否准确 | **否** |
| `unbranded_recommendation` 推荐题（不带品牌名） | 只描述需求，反映能否被推荐 | 是 |
| `comparison_scenario` 对比 / 场景题 | 带约束条件的选择 | 是 |

认知题里出现品牌是必然的 —— 把它算进推荐率会把数字做得很好看，但那是自欺。
因此 `categoriesForRecommendation()` 只返回后两类，分类覆盖检查也会在
"只有认知题"时专门警告。

### 2. 采样协议（`sampling_protocols`）

把"在什么条件下采的"固定下来。协议记录：问题集 + 版本、平台、每问重复次数、
地区、**是否联网检索**、采样界面（消费者界面 / 官方 API）、定位方式、锚点、
时段、模型版本、指纹、来源协议、锁定时间。

设计要点：

- **协议必须基于已冻结的问题集**：未冻结的问题还会变，条件就不固定
- **指纹相同不会重复建协议**：否则同一组真实条件被拆成两份，数据随之拆散
- **指纹包含模型版本**：模型版本属于"可比但必须记录"的条件。
  不进指纹会导致"换模型的复测协议"被当成重复协议复用，既建不出新协议，
  也丢了 `cloned_from` 这条来源线索（这一点是验收时发现的）
- **平台名归一化去重**：`["FixtureAI","fixtureai"]` 与 `["FixtureAI"]` 是同一份协议

### 3. 指标按协议分组，跨协议不混算

- `sampling_runs.protocol_id`；`response_samples.web_search` 随批次冻结
- `describeProtocol()` 给出可读摘要，`compareProtocols()` 输出差异清单
- **阻断级**（变了就不能比）：问题集与版本、平台、重复次数、联网开关、界面、定位方式、锚点
- **警告级**（可比但需注明）：地区、模型版本、时段
- `cloneProtocol()` 只接受环境类覆盖（地区 / 模型版本 / 时段 / 锚点）——
  不提供覆盖平台、联网、界面的参数，而不是靠调用方自觉
- **未绑定协议的批次被单独列出**，明确标注"不参与任何前后对比"

### 4. 运营台

- `/console/protocols`：协议清单（含指纹、可比性徽章、批次与样本数）、
  复制为复测协议、新建协议、三类问题说明
- `/console/questions`：每条问题的分类下拉 + 分类覆盖提示
- `/console/sampling`：批次绑定协议 + "本批次是否联网检索"开关

## 未实现（明确不承诺）

- 不做按分类分组的指标视图（B3 的职责）
- 不做协议条件的部分冻结（例如"只锁定平台"）—— 协议是整体锁定的
- 不做模型版本自动探测：平台不会通过界面告知当前模型，只能人工记录
- 不做问题集的自动分类：分类由人工判断；启发式猜错会直接污染统计口径

## 顺带修掉的两个真实缺陷

验收时发现，两者都会导致**数据被拆散或来源丢失**：

1. **协议指纹漏了 `modelVersion`。** 复制协议时只改模型版本，会因指纹相同而
   复用基线协议 —— 建不出复测协议，`cloned_from` 也没写入。
2. **指纹没对平台名去重。** `["FixtureAI","fixtureai"]` 会被当成另一份协议。
