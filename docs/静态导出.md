# 静态网站导出 —— 已实现 / 未实现

把审核通过的内容导出为可直接上传到 Pages 的静态包。
基准提交 `e661581`。

## 为什么需要它

当前项目是一个完整的 Next.js 应用：**按需渲染的页面 + SQLite + 运营台 + API**。
它不能直接拖拽上传到静态托管 —— 没有 Node 运行时、没有数据库、也没有后端。
所以导出路径单独走一条：本地系统继续保存客户资料、审核内容、记录采样、生成报告；
上传到 Pages 的只有公开 HTML、图片和样式。

## 用法

```bash
STATIC_EXPORT_BASE_URL=https://geo.example.com \
SITE_NAME=你的站点名 \
pnpm export:static [输出目录] [--assets <资源目录>]
```

默认输出 `static-site/`，整个目录上传即可（含 `.nojekyll`，GitHub Pages 会按原样发布）。

## 三条硬规则

### 1. 只导出已公开内容

门店/品牌页取 `public_pages.status='published'` 的快照，文章取已成功发布的知识页。
草稿、待审核、已下线一律不导出，并在导出日志里逐条说明"为什么它没被导出"：

```
[export]   跳过 store「某门店」：还是草稿 —— 未提交审核
```

这是"运营台里出现过的内容不会自动公开"在导出路径上的同一道闸。
验收脚本建了一个草稿门店，断言它**不出现在任何页面里**。

### 2. 必须提供真实域名

canonical 与 sitemap 会写进导出物。写 localhost 会让搜索引擎与 AI 爬虫
据此建立错误的规范地址 —— 比不导出更糟。所以没有明确域名就直接拒绝：

```
拒绝导出：必须提供可公开访问的域名。
```

本机地址（`localhost` / `127.0.0.1` / `*.local`）与非法 URL 一律拒绝。

### 3. 导出物里不能有任何内部信息

`scanExportSafety()` 逐文件检查，命中即**拒绝产出**（不留半成品目录）：

| 检查项 | 例子 |
|---|---|
| 运营台路径 | `/console` |
| API 路径 | `/api/` |
| 数据库引用 | `.db` |
| 环境变量 / 密钥名 | `CONSOLE_PASSWORD`、`DATABASE_PATH` |
| Next.js 构建产物 | `/_next/` |
| 本机地址 | `localhost`、`127.0.0.1` |
| 内部字段 | 截图路径 |

一旦上传，这些信息就已经在公网上了，事后删除也可能已被抓取 —— 所以宁可不出。

## 产出物结构

```
static-site/
├── index.html                  # 索引：门店 / 品牌 / 文章分组列出
├── style.css                   # 单文件样式，无构建、无 CDN 依赖
├── sitemap.xml                 # 只含已公开页面
├── robots.txt                  # 全部允许；sitemap 指向导出域名
├── .nojekyll                   # 让 GitHub Pages 跳过 Jekyll 处理
├── export-manifest.json        # 文件清单 + 短哈希，便于确认上传的是哪一次导出
├── assets/…                    # --assets 目录的内容按原样复制
├── stores/<slug>/index.html
├── brands/<slug>/index.html
└── knowledge/<slug>/index.html
```

每个页面都带：`<!DOCTYPE html>`、`lang="zh-CN"`、`<title>`、`meta description`、
`canonical`、共享样式表、JSON-LD（门店 `Restaurant`/`LocalBusiness`、品牌 `Organization`、文章 `Article`）。

## 图片与资源

- `--assets <目录>` 指定资源目录，内容会被复制到输出目录的 `assets/` 下
- **正文里的站内引用一律按站点根书写**：`assets/img/store.jpg`、`/knowledge/x/`。
  导出时会按页面层数转成相对路径（`../../assets/img/store.jpg`）
- **任何一类引用解析不到文件都会导致导出失败**，并逐条列出
  「哪个页面的哪条引用 → 解析成了什么 → 缺哪个文件」
- 未被任何页面引用的资源只给提示（可能是不必上传的冗余文件）
- Markdown 支持图片语法；`data:` 图片被拒（避免页面体积失控），
  逃出站点根目录的路径被拒

### 为什么用相对路径而不是 `/assets/...`

`/assets/...` 只在部署到**域名根目录**时正确。
GitHub Pages 的**项目站**是 `https://user.github.io/repo/`，
根绝对路径会指向域名根而 404。导出物全部使用相对路径，
因此在域名根目录与子路径下都能用（验收里两种部署都真的跑过）。

## 路径约定（一次真实事故的教训）

导出物是「多层目录的静态站」：`stores/<slug>/index.html` 在两层目录里。
**同一个字符串在不同层数的页面里指向不同文件** —— 这是最容易出错、
也最容易被测试漏掉的地方。事故中同时出现了 4 类问题：

| 问题 | 现象 | 原因 |
|---|---|---|
| 门店/品牌页样式表写 `../style.css` | 页面没有样式 | 页面在两层目录，`../` 只回到 `stores/` |
| 门店/品牌页返回链接写 `../` | 返回 404 | 落在没有 index.html 的中间目录 |
| 文章图片写 `assets/img/…` | 图片裂开 | 浏览器在文章目录下找，文件在站点根 |
| 索引页链接写 `/stores/…/` | 子路径部署全 404 | 根绝对路径指向域名根 |

**为什么原来的测试没抓到**：只检查了「文件在磁盘上」+「页面里有这条引用」。
这两件事都成立，页面依然可以是坏的。

现在改为**从每个页面出发，把每条引用解析成文件路径再判断**（`resolveReference`），
并且把导出目录用静态服务器跑起来，**按浏览器的方式逐条请求**：

- 域名根目录部署：每个页面、每条引用都请求一次，全部 200
- 子路径部署（站点挂在 `/site/`）：同样逐条请求，证明相对路径在两个场景都成立

## 未实现（明确不承诺）

- **不做增量导出**：每次全量重建，靠 `export-manifest.json` 的哈希对比确认差异
- **不做图片压缩 / 转 WebP**：按原样复制，避免在导出环节悄悄改变客户素材
- **不做 CDN 或缓存配置**：只产出文件，托管方的缓存策略由使用者决定
- **不导出工具页**（`/tools/*`）与检查结果页：前者依赖服务端检查逻辑，
  后者本就设计为不被索引
- **不做自动上传**：导出与部署分开，上传动作由人执行（避免误发布）
- **不做多站点**：一次导出一个域名；多客户需要分别指定输出目录与域名
